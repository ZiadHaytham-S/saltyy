# Phase 6: السلة والطلبات — تنفيذ ومراجعة

النطاق اتوافق يوم 11 أكتوبر 2026. التنفيذ فوق الـRepository الموجود، من غير إعادة بناء الحسابات أو الكتالوج. المرحلة دي محلية، ومفيش Payment Gateway أو تكامل شحن أو عمولات أو Subscriptions أو DNS.

## اللي اتعمل وليه

- السلة لكل Store Slug لوحده، وlocalStorage فيه Slug المنتج والكمية بس؛ مفيش أسعار موثوقة أو بيانات عميل. Refresh يحافظ عليها. الحد 20 منتج مختلف و100 قطعة لكل بند.
- Quote من NestJS يراجع Active فقط، والأسعار والكميات وإعداد الشحن. المنتج المؤرشف أو المحذوف أو غير المتاح يظهر برسالة في السلة. Quote ما بيحجزش مخزون؛ الحجز عند إنشاء الطلب فقط.
- Checkout يدعم Guest وCOD فقط، للمتاجر المصرية بعملة EGP حاليًا. الحسابات والكتالوج ما زالوا بيدعموا الدول العربية الأخرى؛ الطلبات الدولية محتاجة مرحلة منفصلة للعناوين والشحن.
- الاسم والموبايل المصري والمحافظة والمدينة والعنوان والملاحظات بيتراجعوا بـZod. الأرقام العربية و010/011/012/015 بتتطبع إلى +20. ده فحص صحة صيغة، مش إثبات ملكية الهاتف.
- رسوم شحن ثابتة لكل طلب، من صفر إلى 10000 جنيه. الإعداد الافتراضي null؛ التاجر لازم يحفظ قيمة صريحة حتى لو صفر. مفيش رسوم مخترعة أو ربط بشركة شحن.
- العميل بيشوف الإجمالي قبل التأكيد. Quote Token صادر من الخادم وموقع بـHMAC، لكنه ما بيحددش السعر. عند التأكيد الخادم يعيد القراءة والحساب ويقارن الموافقة بالأسعار الحالية؛ لو السعر أو الشحن اتغير، يُرفض الطلب ويُعرض الإجمالي الجديد للمراجعة.

## ضمانات الطلب والمخزون

الأوردر وخصم المخزون وorderMovements بيتحفظوا في MongoDB Transaction واحدة بـsnapshot read concern وmajority write concern. كل عملية لها نفس session، ومفيش Promise.all أو إرسال إيميل داخل Transaction.

كل بند بيتخصم بشرط `storeId` وActive و`stockQuantity >= quantity`. معاملات الطلبات والكتالوج بتكتب في Store catalogRevision كمان، عشان التعديلات المتزامنة للأسعار/المخزون/الشحن ما تعدّيش من غير إعادة مراجعة. ده بيبسّط الصحة في الـMVP، لكنه بيسلسل الكتابات داخل المتجر؛ اختبار سعة الإنتاج لاحقًا مطلوب.

Snapshot بيحفظ اسم المنتج وSlug والسعر والكمية وإجمالي البند وعنوان العميل ورسوم الشحن وقت الطلب. الأسعار بالجنيه محسوبة كأعداد صحيحة بالقروش، مع Safe Integer وحدود للإجماليات. تحديث سعر المنتج أو الشحن لاحقًا ما بيغيرش الطلب القديم.

Idempotency معناها إن إعادة المحاولة ما تعملش طلب جديد. المتصفح بيولد مفتاح عشوائي 256 bit لكل محاولة، وNestJS بيحفظ SHA-256 للمفتاح وRequest Hash مع الطلب. Unique Index على `(storeId, idempotencyHash)` يمنع تكراره حتى مع المنافسة. نفس المفتاح ونفس البيانات يرجعوا نفس الأوردر؛ تغيير البيانات يرجع Conflict. المفتاح بيستمر طول ما سجل الأوردر موجود، من غير TTL يمسح الحماية.

المفتاح موجود في sessionStorage من غير بيانات العميل. لو الاتصال انقطع بعد الحفظ، Checkout يراجع نفس المفتاح قبل إتاحة محاولة جديدة. المتصفح ما بينشئش مفتاحًا جديدًا لمجرد فشل الشبكة. مسح بيانات المتصفح أو استخدام جهاز آخر يزيل إثبات المحاولة؛ لو سبق تأكيد الطلب، العميل يتواصل مع المتجر بدل إعادة الطلب عشوائيًا.

## الخصوصية والصلاحيات

- Merchant API يستخرج Store من صاحب Session؛ Store ID من المتصفح لا يمنح صلاحية. القراءة والتعديل والقوائم كلها scoped.
- قائمة الطلبات تعرض الرقم والتاريخ والحالة والإجمالي فقط. تفاصيل العميل موجودة في صفحة التاجر المحمية. النصوص المعروضة تُعامل كنص، وليس HTML.
- مفيش Public endpoint للقراءة بـOrder ID. التأكيد يحتاج Receipt Token مشتق من المفتاح العشوائي مع domain separation؛ MongoDB تخزن Hash فقط. الرابط يستخدم URL fragment، والصفحة تمسحه قبل عرض النتيجة. sessionStorage يحفظ إثبات التأكيد لنفس التبويب لدعم Refresh، وليس بيانات العميل أو Merchant Session.
- Receipt صالح 7 أيام، ويرجع `orderNumber` و`status` فقط. لا اسم ولا موبايل ولا عنوان ولا بنود. امتلاك رابط التأكيد يمنح عرض النتيجة المحدودة فقط.
- Origin وCSRF وJSON allowlist موجودة حتى للطلبات العامة المتغيرة. الردود `no-store`، ولا يتم تسجيل Body أو Tokens أو بيانات العملاء.
- Rate limits تعتمد على IP الحقيقي للاتصال، وليس X-Forwarded-For غير الموثوق: Checkout 30/10 دقائق، Quote 60/دقيقة، Recover وReceipt كل منهما 30/5 دقائق. حدود موزعة/Proxy موثوق وخطة التعامل مع شبكات NAT تُراجع قبل النشر.

## حالات الطلب

`PENDING → CONFIRMED → PROCESSING → SHIPPED → DELIVERED`

الإلغاء مسموح من PENDING أو CONFIRMED أو PROCESSING فقط. الإلغاء نهائي ويعيد المخزون مرة واحدة في نفس Transaction، مع سجل RESTORE فريد وعلامة stockRestored. Version يمنع تحديثين متعارضين لنفس الطلب. المنتج المؤرشف يستقبل مخزونه المرتجع بدون نشره. لو استعادة المخزون هتجاوز الحد الأقصى أو المنتج غير موجود، العملية كلها تفشل بأمان.

SHIPPED لا يُلغى بزر عادي، وDELIVERED وCANCELLED حالات نهائية. المرتجعات وفشل التسليم والتسويات بعد الشحن مؤجلة؛ لا يوجد Refund إلكتروني. DELIVERED حالة يسجلها التاجر يدويًا، وليست تأكيدًا من شركة شحن أو تسوية مالية.

الحجز يبدأ عند PENDING ويستمر حتى التنفيذ أو الإلغاء؛ مفيش إلغاء تلقائي للطلبات المعلقة. التاجر لازم يراجع طلبات COD ويتأكد من العميل قبل الشحن. Rate Limiting يقلل الإساءة، لكنه لا يثبت أن كل طلب Guest حقيقي.

## إزاي تجرب

1. شغّل MongoDB replica set باستخدام `pnpm db:start` و`pnpm db:init` إذا لم تكن شغالة، ثم `pnpm dev`.
2. سجّل كتاجر بمتجر مصري، وافتح Dashboard → الشحن، واحفظ 35 جنيه مثلًا أو صفرًا.
3. أضف منتج Active بمخزون وسعر، ثم افتح `/store/STORE-SLUG` في نافذة خاصة.
4. أضف المنتج للسلة، جرّب الكمية وRefresh، ثم Checkout. أدخل بيانات مصرية صحيحة وأكد COD.
5. صفحة التأكيد تعرض رقم الطلب فقط مع الحالة، ويمكن Refresh في نفس التبويب.
6. في Dashboard → الطلبات افتح التفاصيل. جرّب التأكيد والتجهيز والشحن والتسليم. جرّب الإلغاء على طلب آخر قبل الشحن، وراجع رجوع المخزون.

## الاختبارات وحدود التجربة

`pnpm test` و`pnpm test:integration` و`pnpm test:web` و`pnpm typecheck` و`pnpm lint` و`pnpm build`.

Integration على قاعدة مؤقتة في replica set حقيقي: أسعار مزورة، منتجات غير نشطة أو خارج المتجر، تغيير السعر/الشحن، خمس محاولات متزامنة لنفس الطلب، ستة عملاء لآخر قطعة، فشل كتابة DB وRollback، إلغاء متزامن واستعادة مرة واحدة، دورة الحالات، منع تسريب البيانات، Rate Limiting وIdempotency بعد إعادة المحاولة.

E2E يستخدم Edge وبيانات MongoDB مؤقتة، ويجرب السلة وRefresh والعزل وCOD وتأكيد خاص والإلغاء ودورة الحالات. كمان يحاكي حفظ الطلب ثم ضياع الرد، ويتأكد إن Refresh يسترجع الطلب من غير تكرار. صور التجربة في `.local/test-artifacts`.

نتائج 11 أكتوبر 2026: 15 Unit و43 Integration نجحوا، مع TypeScript وLint وBuild. رحلة Edge على Production Build منفصلة نجحت، بما فيها الحسابات وOTP واستعادة كلمة المرور والكتالوج والمتجر العام والطلبات، ودعم RTL/LTR وDark/Light. قواعد الاختبار بيانات مؤقتة، والإيميلات تروح SMTP محلي، من غير تعديل بيانات متجرك أو إرسال إيميلات للعملاء.

أثناء المراجعة اتصلح توقيت التنقل في اختبار المتصفح: كان حقل اسم المنتج يطابق خانة البحث في الصفحة السابقة، وحقل الإيميل يطابق Login قبل فتح Forgot Password. الاختبار دلوقتي ينتظر URL الصحيحة ويستخدم Labels دقيقة، ويتحقق إن اسم المنتج موجود بعد الرفع. مفيش تجاهل لاختبار فاشل.

اختبار إضافي يحاول إلغاء طلب بمنتجين، ويجبر استعادة المنتج الثاني تفشل عند حد المخزون؛ المخزون المستعاد للمنتج الأول وسجلات RESTORE وحالة الطلب كلها بتتراجع. بعد إصلاح السبب، الإلغاء ينجح ويرجع القطع مرة واحدة. الشحن المجاني الصريح وصفر بالأرقام العربية متجربين أيضًا.

الاختبارات المحلية مش ضمان 100% ضد كل خطأ. قبل استقبال عملاء حقيقيين: تجربة Safari/iOS وأجهزة فعلية، اختبار الحمل، انقطاع/Failover لقاعدة البيانات، نسخ احتياطي واسترجاع، HTTPS وProxy وبيئة نشر، سياسات الخصوصية والاحتفاظ ببيانات العملاء، وقواعد المرتجعات وتأكيد COD. دي مراجعة نشر منفصلة تحتاج موافقة، ولا تتفعّل ضمن Phase 6.
